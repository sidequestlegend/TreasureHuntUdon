## 2. Feature checklist

Each line is a testable statement of what upstream does. "Prefab value" means the value shipped in
`THP`/`PPP`. Items marked (Q) are quirks or faults; section 10 says which are reproduced.

Setup
1. On start each client builds the pool: for every child of "Treasures (Drop treasures here)", in order, it creates a wrapper (clone of `Container_Parent`: Animator plus child `Rotator`) named like the treasure, moves the treasure under `wrapper/Rotator` keeping its local transform, and puts the wrapper under `TreasuresContainer`. `THC:84-95`.
2. The prefab pool is 9 treasures: index 0-4 "Coin", 5-7 "Gem" (three different gem meshes), 8 "Star". `THP:10977`, `THP:1098`, `THP:2440`, `THP:3164`, `THP:1850`, `THP:1468`, `THP:467`, `THP:3944`, `THP:666`.
3. All wrappers start hidden. `THC:97-101`.
4. `isAnimated` (prefab value true): when false the wrapper's Animator is disabled. When true the `Rotator` turns 360 degrees about Y every 4 s, linear, looping. `THC:91`, `THP:190`, `Animations/Treasure_Rotator.anim` (Euler curve 0 to 360 over 4 s, `m_LoopTime: 1`).
5. `isTreasureHunt` (prefab value true): each treasure gets an invisible "return button", a clone of `Item_Despawner` (sphere trigger collider radius 0.5, mesh renderer disabled), parented to the treasure mesh, named with the pool index, and scaled per axis so its renderer bounds match the treasure's renderer bounds. `THC:108-117`, `THC:252-268`, `THP:4162-4318`.
6. With `isTreasureHunt` false there are no return buttons: treasures cannot be found, and the system is a random spawner that stops once `amountOfTreasuresActive` are out. `THC:14`, `THC:108`.
7. The synced arrays are sized to the pool. `THC:104-105`.

Spawning
8. Only the owner of the controller object counts down and spawns. `THC:67`, `THC:169`.
9. Each cycle the timer is set to a uniform random float in [`timerMin`, `timerMax`] (prefab values 0 and 5 s). The owner subtracts frame time every frame and makes one spawn attempt when it reaches 0 or less. `THC:69-76`, `THC:130`, `THP:192-193`.
10. One attempt spawns at most one treasure. `THC:185-193`.
11. No spawn while the number of visible wrappers on the owner is at least `amountOfTreasuresActive` (prefab value 5, script default 1). `THC:177-185`, `THP:191`, `THC:23`.
12. The treasure is chosen uniformly among pool entries whose flag is false, so a kind's chance follows how many copies of it are still hidden (5 Coin, 3 Gem, 1 Star). `THC:204-236`, `README.md:20`.
13. The zone is chosen uniformly among all BoxColliders under "Locations" (three in the prefab; the colliders are disabled triggers and need not be enabled; more boxes in an area raise its chance). `THC:84`, `THC:187`, `THP:833`, `README.md:17-18`.
14. The position is uniform inside the chosen box: a local point within plus or minus half the collider size on each axis, transformed by the zone's transform (position, rotation, scale). The collider's `center` is ignored. `THC:239-249`.
15. On a spawn: flag true, world position stored, timer re-rolled, state serialised, `ReplicateStates` sent to everyone. `THC:190-198`.
16. `ReplicateStates` on every client shows or hides each wrapper by its flag and moves it to its stored world position. `THC:135-156`.
17. If every wrapper is visible (pool exhausted) the attempt only re-rolls the timer; nothing is sent. `THC:170-175`, `THC:269-280`.
18. If the cap is reached but the pool is not exhausted, the attempt still serialises and sends `ReplicateStates`, so every client is refreshed once per timer period. `THC:185-198`.
19. A found treasure's pool slot is free again; it can respawn later at a new random place.
20. (Q) `timerMin = timerMax = 0` is documented as "spawn immediately" (`THC:28`). By reading: `StartSpawnCycle` calls `SpawnTreasure`, which calls `StartSpawnCycle` again (`THC:124-127`, `THC:196`); the visible count does not change inside that chain, so it keeps spawning until every flag is true and then writes `isTreasureActive[-1]` (`THC:189-190`, `THC:217-221`), which should halt the behaviour on the owner.

Finding and returning
21. A treasure is found with VRChat "Interact" on its return button: interaction text "Found!", proximity 0.7 m. It is not a pickup and not a touch trigger. `TR:22`, `THP:4306-4308`.
22. Interact calls `ReturnItem(index)`: the finder takes ownership of the controller if it is not the owner, sets the flag false, serialises, and sends `ReplicateStates` to everyone. `TR:25`, `THC:157-163`, `THC:282-285`.
23. The finder's saved count for that treasure is raised by 1. The key is the name of the treasure object ("Coin", "Gem", "Star"), the value an int. `TR:28-30`.
24. The treasure disappears for everyone. `THC:139`.
25. When a return button is disabled, each client creates a `Pick_Treasure_Animation` at its position: one burst of 30 particles (sphere emitter, lifetime 0.2 to 1 s, size 0.1 to 0.3, speed 0.68, trails, noise), and the pick sound (0.67 s, 3D, min 1 m, max 10 m, volume 1). The effect destroys itself after 2 s. Everyone present sees and hears it. `TR:35-38`, `THP:4443-9395` (`stopAction: 2`, burst `scalar: 30`, shape `type: 0` at `THP:5074`).
26. After a find the finder owns the controller and therefore runs the spawn loop from then on. `THC:159`, `THC:67`.
27. (Q) Nothing stops two players interacting with the same treasure in the same moment; each runs items 22-23, so both are credited. By reading.
28. There is no per-player limit, cooldown, round, timer display or end of game. The hunt runs for as long as the instance exists.

Personal list ("found:")
29. A world-space panel titled "found:" shows one row per distinct treasure name, in order of first appearance in the pool (Coin, Gem, Star), with the local player's saved count. `PSL:40-100`, `THP:397`.
30. It is built 1 s after start and rebuilt whenever any player's saved data changes, or any player joins or leaves. `PSL:29`, `PSL:157-183`.
31. Each player sees only their own numbers there. A missing key shows 0. `PSL:67`.

Scoreboard
32. A world-space scoreboard shows one list per distinct treasure name, side by side (spacing 41.97 canvas units), each titled with the treasure name. `SB:38-61`, `SB:91-101`, `THP:10288-10313`.
33. Each list has one row per player **currently in the instance**: display name and that player's saved count for that treasure. `SB:63-85`, `SB:102-123`.
34. Lists are built 1 s after start, rows one frame later; rows are rebuilt on any player's data change, join or leave. `SB:25-37`, `SB:167-182`.
35. (Q) Row order comes from `SortListOfDictionaries` (`SB:184-207`). It is meant to be highest first. It reads the outer score once and never refreshes it after a swap, so it is correct for up to three players and can be wrong from four: a re-statement of the loop over 21,844 small inputs gave 3,463 not in descending order (for example scores in join order 0,0,2,1 are shown as 2,0,1,0).
36. Players who are not present are not listed. There is no all-time table.
37. Rows past the list's mask are clipped (about 16 rows fit: list height 910.5, row 50, spacing 4.53; `THP:3265-3312`). By layout reading.
38. The three `HiScoreList (n)` objects in the prefab are editor-only positioning templates ("Positioning template will be removed automatically") and are not in a build. `THP:1949`, `THP:3379`, `THP:9442`, `THP:3567`.
39. Scores on both boards are **counts of finds**. Points exist only in the prize (item 41).

Prize
40. Prize settings (prefab values): names Coin, Gem, Star; points 1, 5, 10; cost 30. `PPP:62-67`.
41. Total = sum of saved count times points. It is evaluated when the local player's saved data updates (first load and every find) while the object is not yet eligible. `PP:66-73`, `PP:92-100`.
42. When total reaches the cost: `WinSequence` is sent to everyone, the eligible flag is set and serialised. `PP:74-81`.
43. The flag's change callback shows "Container (Drop prize here)", which starts hidden, on every client. `PP:33-46`, `PPP:135`.
44. `WinSequence` on every client moves the `WinSound` audio source to the head position of the object's owner and plays the win sound (2.33 s, 3D, min 1 m, max 10 m). `PP:102-106`, `PPP:184-210`.
45. The prize object is a VRChat **PlayerObject with persistence** (`VRCPlayerObject` and `VRCEnablePersistence`, `PPP:96-119`; class names resolved from the DLL file ids, see section 5). By VRChat behaviour: every player in the instance gets their own copy, owned by them, and the copy's synced flag is saved for that player and restored on every later visit. So the container is visible to everyone while an eligible player is present, and there is one prize per eligible player. `README.md:22-23`.
46. The flag is never cleared; no code path sets it false.
47. Demo prize content: a "Cheese" model that can be picked up (VRCPickup, proximity 2 m), kinematic rigidbody, box trigger collider, position synced. `PPP:280-492`.
48. (Q) By reading: `OnPlayerDataUpdated` has no ownership test (`PP:95`), so when my data updates every copy on my client that is not yet eligible runs the check with **my** totals. If I qualify, my client shows the container of every such copy locally, and sends `WinSequence` on each, so everyone hears one win sound per copy, each at that copy's owner's head. `WinSequence` reads `_owner`, which is only set in `OnPlayerRestored` (`PP:86`, `PP:104`), and would fault if it ran first.

Persistence and edge cases
49. Saved counts belong to the VRChat account and the world, and survive leaving, new instances and other devices (VRChat `PlayerData`). `TR:29-30`, `README.md:3`.
50. Treasure flags and positions belong to the instance and are not saved.
51. Late joiner, by reading: boards appear after 1 s. Treasures appear on the next `ReplicateStates` from the owner (within one timer period), because there is no `OnDeserialization` handler; if the pool is exhausted nothing is sent (item 17) and the joiner sees no treasures until someone finds one.
52. Owner leaves, by reading: VRChat gives the controller to another player; that client's `Update` continues with its last received `spawnTimer`. No script handles the transfer.
53. No UI is interactive: no buttons, no UnityEvents, no input fields. `THP` contains only Image, Mask, layout groups, TMP text, CanvasScaler, GraphicRaycaster.
54. Sounds: pick and win only. No music.

### 3.4 Persistence on Altspace: what is kept, what is lost, and the design

Platform facts: no per-player saved data except `localStorage` (`SDK/Docs/javascript-api/saving-data.md:12`: "There is no built-in way to save a player's own progress between visits"); user state is written only by its owner, read by everyone, and removed 30 s after the session closes (`RELAY:140`, `RELAY:210`); space state can be written by anyone in the room and expires 24 h after the last change (`RELAY:340`).

Design (three stores, one job each):

| Store | Key | Value | Role |
|---|---|---|---|
| `localStorage` | `pk1.treasure-hunt.<inst>.<uid>.pd` | `{"v":1,"c":{"Coin":12,"Gem":3,"Star":1}}` | The saved counts. Stands in for `PlayerData` |
| `localStorage` | `pk1.treasure-hunt.<inst>.<uid>.pz` | `"1"` once unlocked | The saved prize flag. Stands in for the persisted PlayerObject flag |
| User state (2 of the 4 allowed leaves) | `pk1.treasure-hunt.<inst>.pd`, `pk1.treasure-hunt.<inst>.pz` | same strings | What everyone else reads: my counts for the scoreboard and my prize flag |
| Space state | `pk1.treasure-hunt.<inst>.v.<controller>` | flags, positions, timer | Treasures only. Nothing personal |

Flows: on join, read `localStorage`, publish both leaves, then raise the local "data updated" callback (stands in for `OnPlayerRestored` and the first `OnPlayerDataUpdated`). On a find, add 1 in `localStorage`, republish `pd`; everyone's scoreboard refreshes on the user-state change (stands in for `OnPlayerDataUpdated(player)`). On reaching the cost, set `pz` in both, send `WinSequence`. Space state is not used for totals because any page in the room can overwrite a public key.

| Feature | Kept | Lost |
|---|---|---|
| Personal totals (item 29-31, 49) | Counts survive leaving and coming back, new room instances of the same world, and app restarts, on the same device and account. Scope is one world, as upstream | Totals do not follow the account to another device (a headset and a PC count separately). Clearing app data or reinstalling wipes them. They are tied to the world's web address and to the instance key: renaming the world handle, or removing and re-adding the snippet, orphans them |
| Scoreboard of everyone present (item 32-36) | The same board: every present player, per-kind counts, live on find, join and leave. Nobody can write another player's numbers | Each row is what that player's device holds, so a player on a second device shows that device's totals. A leaver's state lingers 30 s on the relay; the board lists present players only, so the row still goes at once |
| Prize unlock (item 40-46) | Unlock is sticky and saved; while an eligible player is present everyone sees the prize; everyone hears the win sound at the winner's head | Per device, not per account. One prize for the room, not one per eligible player (no PlayerObjects). A creator cannot drop arbitrary content into the container (section 8 gives a hook) |

### 3.5 Port wire summary

- Space state: `ref` (runtime) and one leaf `v.<controller>` = `{g, n, w, d}`, where `d` holds the flags, the positions (three numbers per treasure, rounded to millimetres) and the timer. Under 1 KB at the largest pool (22 treasures).
- One-shot: `{"pk":1,"g":"treasure-hunt","i":"<inst>","t":"WinSequence","u":"<uid>","p":[x,y,z]}`. `ReplicateStates` is not sent (section 10.1, row 6).
- Traffic: one leaf write per acting spawn cycle (about every 2.5 s at the defaults) and one per find; one user-state write per find and two on join.

### 8.2 Gizmos, and a limit that affects the plan

Per placeable: one `position` handle and one shape.

```html
<bs-gizmo type="position" attribute="position"/>      <bs-gizmo type="plane" attribute="position" size="1.6 0.73"/>
<bs-gizmo type="position" attribute="personal-list"/> <bs-gizmo type="plane" attribute="personal-list" size="0.28 0.22"/>
<bs-gizmo type="position" attribute="prize-position"/><bs-gizmo type="sphere" attribute="prize-position" radius="0.15"/>
<bs-gizmo type="position" attribute="zone1"/>         <bs-gizmo type="box" attribute="zone1" size="1.377 0.792 0.642"/>
... the same pair for zone2 to zone8
```

**A gizmo binds position only.** Its `size`, `rotation` and `radius` are literals on the `<bs-gizmo>` child, read once (`SDK/Editor/BSSnippetEditor.cs:456-462`, `:486-494`). So a creator can drag a zone, but the drawn box does not follow `zoneN-size` or `zoneN-rotation`, and the Inspector shows no field for a gizmo's own attributes. Three ways through, in my order of preference:

1. Settings as above plus `show-zones="true"`, which draws the true boxes in Play mode. Keeps rotated zones and a line-for-line position routine. The Scene-view box is only right for the default sizes unless the creator edits the `size` literal by hand.
2. Two corner handles per zone (`zoneN-a`, `zoneN-b`): both ends draggable in the Scene view with what the SDK already has; loses rotated zones.
3. A small SDK change so a box can take its size from a setting. Best for creators; needs the SDK owner.

As built (option 1, `TreasureHuntKitBuilder.SnippetGizmos`): a handle and a plane for the personal list, a handle and a
sphere for the prize, a handle and a box at the default size for zones 1 to 3, and a handle only for the spare zones 4 to
8 (their default size is 0, so a box would draw nothing). They follow the kit's own position handle and box.

### 9.2 Node scenarios (several clients on the fake room, virtual time)

1. One client: within `timer-max` a treasure appears inside a zone; never more than `max-active`; never the same index twice.
2. Pool mix: over 2,000 spawns the kind shares follow the remaining pool; every position is inside its zone, including a rotated one.
3. Find: A clicks; A's count +1 in storage and user state; the treasure hides on A, B and C; exactly one pick effect each.
4. Two clients click the same treasure in the same tick: both hide it; credit as decided in section 10 (one credit, or two as upstream).
5. Out of reach: a click from beyond `find-distance` does nothing.
6. Hand-over: after B finds, B spawns; B leaves; spawning continues within one period.
7. Referee loss and joins in random order: state digests match on all clients at the end.
8. Late join: C joins with five treasures out and sees all five before the next spawn; no pick effects for treasures already hidden.
9. Scoreboard: three clients with different saved counts; rows match the `rows` vectors; a find by B updates B's row everywhere; C leaves and the row goes.
10. Seventeen players: sixteen rows shown, no error.
11. Persistence: A finds three, leaves, rejoins with the same storage: totals are back on both boards. With empty storage: zeros.
12. Prize: A reaches 30 (for example 3 Stars): one `WinSequence`, container on for all; B joins later and sees it; A leaves and it hides; A returns and it shows without a second win sound.
13. Prize threshold from settings; changing points changes the result.
14. Two hunts in one room plus another game: no shared keys, messages or storage.
15. Bad settings: zero-size zones only, `timer-min` above `timer-max`, both timers 0, counts above the kit maximum: no exception, documented clamps.
16. Budget: writes per second stay under the shared 20 per second bucket with `timer-max` at its minimum; leaf size under 16,384 bytes at the largest pool.

### 9.3 Play mode, one player (scenario bot, PASS/FAIL lines)

1. Kit loads from a local server; all bindings resolve; boards show titles Coin, Gem, Star and "found:".
2. A treasure appears, spins, and is inside the zone drawn by `show-zones`.
3. The bot clicks it from within reach: it hides, particles and sound play, the personal list goes 0 to 1.
4. Exit and re-enter Play: the count is still 1.
5. With `prize-cost="1"`: win sound, prize shows, the cheese can be grabbed.
6. `animated="false"`: no rotation. `treasure-hunt="false"`: clicks do nothing.

### 9.4 Local Multiplayer, two players

1. Both pages reach the same state digest after 60 s of spawning.
2. Player 1 finds: player 2 sees it hide with the effect; both scoreboards show two rows with the right numbers.
3. Player 2 reloads (late join): same treasures, same boards.
4. Player 1 unlocks the prize: player 2 hears the win sound and sees the prize; player 2 grabs the cheese and player 1 sees it move.
5. The player who last found closes: the other keeps getting new treasures.
6. Two snippet copies with different zones: finds in one do not change the other.

### 10.2 Open risks and questions, ranked

1. **Licences.** Both sounds are from a commercial library and the font is "All Rights Reserved"; five textures and the cheese have no stated origin. Decision needed: replace all (my recommendation), and ask the author about `Treasures.fbx`.
2. **Per-device saving is the heart of a "persistence game".** Is that acceptable? The SDK's own answer is "keep it on your own server"; `user.uid` is the same on every visit (`SDK/Docs/javascript-api/user-multiplayer.md:12`), but it is public, so a server would need some proof of identity. Out of the plan's scope; raised because it would restore the main feature.
3. **Zone size cannot be shown by a gizmo** (section 8.2). Pick option 1, 2 or 3.
4. **Runtime calls this game needs that README does not list**: present-player list with join and leave, read and write of user-state leaves, a data-changed callback, elapsed time in `Update`, accepted-write feedback, a way to stop an Animator. If the runtime is frozen after chess without them, this port needs game-local workarounds.
5. **Clicks on kit-loaded colliders in the app** (the plan's known risk). This game's only input is that click.
6. **Reach on a flat screen.** 0.7 m from the head may not reach a treasure near the floor if the app has no crouch. May need a larger default on desktop.
7. **Row order fault** (item 35): fixed (coordinator decision), section 10.1 row 11a.
8. **Instance key stability.** Saved totals hang on `<inst>`; README falls back to the element's index, which changes if a creator reorders or removes snippets. Recommend setting `room`.
9. **The prize grabbable** is a networked object under a container that starts hidden; whether ids and sync initialise while hidden is unverified.
10. **About 200 relay refs and up to about 100 text updates per scoreboard refresh.** Cost through the Visual Scripting bridge on Quest is unknown; send only changes.
11. **Is `uid` stable for guests?** If not, guests start from zero every visit.
12. **Float32 against double** in `spawnTrace` vectors: the tick at which a timer crosses zero can differ; use `Math.fround` or compare with tolerance.
13. **`DataDictionary.GetKeys()` order** is assumed to be insertion order; list order (Coin, Gem, Star) rests on it.
14. **Return-button size** depends on renderer bounds read while the wrapper is hidden (`THC:100`, `THC:254-257`); the kit builder should compute it from the visible mesh and a person should check the click volumes.

### 10.3 Trust: what a modified client can still do

The port's authority is the referee (a client), as upstream's is whoever owns the controller. Compared with upstream:

| What | Upstream (VRChat) | Port | Why not closed |
|---|---|---|---|
| Find from a distance | Anywhere: Interact's 0.7 m is the finder's own client | Within `find-distance` + 2.5 m of the head the **referee's app** shows for the finder (10.1 row 12a). Closer than that, a modified client can still take a treasure it has not walked right up to, and can do it as soon as one spawns in range (a bot) | The head reading comes from the avatar's networked pose, which lags; less slack would refuse honest finds made while walking. The app does not say where a remote player's hands are |
| Saved counts | Each player's own `PlayerData`, written by their own client | The same: each player's counts are their own user state and `localStorage` (PlayerData.ts). A modified client can write any count for itself; the scoreboard shows it, and the prize flag it sets shows the prize to everyone while it is present | User state is written only by its owner; nothing else on the platform can vouch for a count (no server). Equal to upstream |
| Hunt state | The synced arrays, writable by whoever takes ownership (any client, at will) | The synced arrays are public space state: a modified page can hide or move treasures, or write another player's session into `foundBy` with a new serial, which credits that player once (an older serial written back no longer does: 10.1 row 12b) | Public space state has no writer check (portkit README, Trust). Equal to upstream |
| The referee seat | Instance master, chosen by VRChat | Claimed by the client ranked first; a modified client can take the seat and then accept its own finds from anywhere | No server decides who is referee (portkit README, stated limit) |
| Whose head | (none) | Get User State matches the id the referee asks for against each user's session id, account id **or display name**: a player whose display name equals the finder's session id could stand in for them. Needs a second account with that name in the room | The SDK node takes one string and matches all three (`GetUserState.cs`); no node takes a session id alone |
